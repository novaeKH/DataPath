# 09. Память, GC и GIL

## Модель памяти без магии

Имя в Python ссылается на объект. Объект живёт, пока на него существуют сильные ссылки или пока сборщик не обнаружит недостижимый цикл.

```python
items = [1, 2]
alias = items
del items
print(alias)  # объект всё ещё жив
```

`del` удаляет имя или элемент контейнера, а не обязательно объект.

## Подсчёт ссылок

CPython в основном освобождает объект, когда его reference count становится нулём. Это обеспечивает предсказуемое освобождение большинства объектов.

```python
import sys

value = []
print(sys.getrefcount(value))
```

Число временно увеличено самим вызовом `getrefcount`, поэтому оно полезно только для диагностики, а не для бизнес-логики.

## Циклический garbage collector

Подсчёт ссылок не может освободить цикл:

```python
a = []
b = [a]
a.append(b)
```

Даже после удаления имён объекты ссылаются друг на друга. Generational GC периодически ищет недостижимые циклы контейнеров.

Обычно вручную вызывать `gc.collect()` не нужно. Частые принудительные сборки могут замедлить программу.

## Почему память не всегда возвращается ОС

Освобождённая память может остаться у Python allocator для повторного использования. Поэтому RSS процесса не обязан сразу уменьшаться. Это не всегда утечка.

Настоящая проблема возникает, если ссылки продолжают храниться:

- глобальный список постоянно растёт;
- кеш не ограничен;
- closure держит большой объект;
- callback или listener не удаляется;
- DataFrame копируется много раз;
- модель и optimizer остаются на GPU.

## Shallow size и реальный размер

`sys.getsizeof` показывает размер только самого контейнера, без объектов по ссылкам.

```python
import sys

rows = [[1, 2], [3, 4]]
print(sys.getsizeof(rows))
```

Для данных важнее профилировать весь процесс и понимать representation: список Python-объектов обычно существенно тяжелее плотного NumPy-массива.

## GIL

Global Interpreter Lock в CPython позволяет только одному thread одновременно исполнять Python bytecode в одном процессе.

Следствия:

- CPU-bound чистый Python редко ускоряется от `threading`;
- I/O-bound задачи могут ускориться, потому что поток ждёт сеть или диск;
- NumPy, PyTorch и другие C/C++ библиотеки могут освобождать GIL во время тяжёлых вычислений;
- несколько процессов имеют отдельные интерпретаторы и GIL, но требуют памяти и сериализации.

## Threads, processes, async

- `threading` — много ожидания I/O и общий адресный простор;
- `multiprocessing` — CPU-bound Python, изоляция, более дорогой обмен;
- `asyncio` — большое число конкурентных I/O-операций в одном потоке;
- vectorized NumPy/PyTorch — обычно лучший путь для численных вычислений.

Не выбирайте инструмент только по слову «параллельно». Сначала определите bottleneck.

## Память в Data Science

Практические правила:

1. Читать только нужные колонки.
2. Проверять `dtype` и cardinality.
3. Использовать category для повторяющихся строк, когда это оправдано.
4. Избегать лишних копий DataFrame.
5. Работать чанками, если данные не помещаются.
6. Осознанно хранить промежуточные признаки.
7. Не превращать NumPy-массивы в списки без причины.
8. Для GPU удалять ссылки и понимать, что allocator кеширует память.

## Профилирование

Полезные инструменты:

- `time.perf_counter` — время участка;
- `tracemalloc` — аллокации Python;
- `memory_profiler` или профилировщик IDE;
- `pandas.DataFrame.memory_usage(deep=True)`;
- `torch.cuda.memory_summary()` для CUDA.

Профилировать следует реальный workload, а не микропример, который не отражает данные.

## Частые заблуждения

- «GIL запрещает любую параллельность» — нет, I/O и нативный код могут выполняться параллельно;
- «`del` немедленно возвращает память ОС» — не гарантируется;
- «высокий RSS означает утечку» — не обязательно;
- «multiprocessing всегда быстрее» — сериализация и копии могут быть дороже;
- «NumPy экономит память только из-за C» — главное: плотный однородный representation без объекта Python на каждый элемент.

## Ответ интервьюеру

CPython использует подсчёт ссылок и дополнительный циклический GC. `del` удаляет ссылку, а не гарантированно объект или RSS процесса. GIL ограничивает одновременное выполнение Python bytecode в потоках, поэтому CPU-bound Python обычно масштабируют процессами или переносят вычисления в векторизованный нативный код. Для I/O потоки и async остаются полезными.
