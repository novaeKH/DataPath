# GroupBy и merge: строим таблицу признаков клиента

Модель должна сделать один прогноз для каждого клиента, а исходные данные содержат много заказов на клиента. Нельзя просто присоединить заказы к клиентам и считать, что готова таблица обучения: число строк изменится.

Сначала определим результат: одна строка — один клиент, признаки — число известных заказов и их сумма. Эта договорённость позволяет осмысленно выбрать агрегацию, соединение и проверку результата.

## Данные разных уровней

```python
import pandas as pd

clients = pd.DataFrame({
    "client_id": [1, 2, 3],
    "city": ["Казань", "Москва", "Пермь"],
})
orders = pd.DataFrame({
    "order_id": [101, 102, 103],
    "client_id": [1, 1, 2],
    "amount": [100., 50., 200.],
})
```

В первой таблице ключ клиента уникален. Во второй клиент 1 встречается дважды, потому что сделал два заказа. Клиент 3 пока не сделал заказов. Ожидаемая итоговая таблица должна всё равно содержать три клиента.

## GroupBy разбивает строки на группы

```python
summary = orders.groupby("client_id").agg(
    order_count=("order_id", "size"),
    amount_sum=("amount", "sum"),
    amount_mean=("amount", "mean"),
).reset_index()
print(summary.to_dict("records"))
# [{'client_id': 1, 'order_count': 2, 'amount_sum': 150.0, 'amount_mean': 75.0},
#  {'client_id': 2, 'order_count': 1, 'amount_sum': 200.0, 'amount_mean': 200.0}]
```

Механизм состоит из трёх шагов: разделить строки по ключу, применить вычисление к каждой группе, собрать результаты. Для клиента 1 берутся суммы 100 и 50: количество 2, сумма 150, среднее 75.

Именованная агрегация явно задаёт имя результата, исходный столбец и операцию. `size` считает строки, а `count` — непустые значения выбранного столбца. Если сумма одного заказа неизвестна, это не означает отсутствия самого заказа.

По умолчанию ключи группировки с пропусками могут исключаться. Если отсутствующий ключ должен образовать отдельную группу для аудита, изучите `dropna=False`.

## agg уменьшает число строк, transform сохраняет

Для итоговой таблицы клиента нужна `agg`. Если требуется показать среднюю сумму клиента рядом с каждым его заказом, используйте `transform`:

```python
orders["client_mean"] = orders.groupby("client_id")["amount"].transform("mean")
print(orders["client_mean"].tolist())   # [75.0, 75.0, 200.0]
```

Значение 75 повторилось у двух заказов клиента 1. Результат выровнен с исходными строками. Это не новое независимое наблюдение и не среднее по всей таблице.

## Соединение с проверкой ожидаемого отношения

```python
features = clients.merge(
    summary, on="client_id", how="left", validate="one_to_one"
)
features[["order_count", "amount_sum"]] = features[
    ["order_count", "amount_sum"]
].fillna(0)
print(features[["client_id", "order_count", "amount_sum"]].to_dict("records"))
# клиент 1: 2 заказа, 150; клиент 2: 1 заказ, 200; клиент 3: 0 заказов, 0
```

Левое соединение сохраняет всех клиентов. Для клиента 3 нет строки в агрегате, поэтому появились пропуски. По условию таблица заказов полна, значит отсутствие заказов можно выразить нулём количества и суммы. Средняя сумма для такого клиента остаётся неизвестной: делить на ноль заказов нельзя.

`validate="one_to_one"` требует уникальности ключа с обеих сторон. Если присоединять справочник клиентов к каждой строке заказов, правильное ожидание будет `many_to_one`.

При двух строках одного ключа слева и трёх справа соединение создаёт шесть комбинаций. Так случайное отношение «многие ко многим» увеличивает выручку без единого исключения Python. До и после `merge` проверяйте число строк, уникальность ключа и контрольные суммы.

## Форма отчёта и момент прогноза

`pivot` превращает значения одного столбца в новые столбцы и требует уникальной пары координат. `pivot_table` сначала агрегирует повторы. `melt` переводит широкий формат в длинный. Эти операции меняют представление, но не создают новых фактов.

```python
long = features.melt(
    id_vars="client_id",
    value_vars=["order_count", "amount_sum"],
    var_name="feature",
    value_name="value",
)
print(long.shape)   # (6, 3)
```

Получилось по две строки на клиента: одна для количества, другая для суммы. Такой формат удобен для сравнения признаков, но не соответствует исходной единице «одна строка — клиент».

Для ML сначала ограничьте заказы моментом прогноза и только затем агрегируйте. Сумма всех заказов за жизнь клиента содержит будущее, если прогноз делается раньше. Даже идеальная проверка `validate` не обнаружит эту смысловую утечку.

## Самопроверка и практика

1. Почему `inner` соединение здесь потеряет клиента 3?
2. Почему среднюю сумму нельзя заполнить нулём по той же логике, что количество?
3. Что произойдёт при повторе ключа в справочнике?
4. Почему `transform` не заменяет агрегацию для таблицы клиентов?

Разбор: у клиента нет совпадения; отсутствие заказов не означает заказ нулевой стоимости; строки могут размножиться, а `validate` обнаружит нарушение ожидания; `transform` сохраняет уровень отдельных заказов.

**Практика.** Добавьте клиенту 2 заказ на 50. Ожидаются два заказа и сумма 250, общая сумма 400. Затем намеренно продублируйте клиента 1 в справочнике и убедитесь, что проверка соединения отклоняет данные.

В визуализации отслеживайте одну строку клиента через группировку и соединение. Следующий урок добавит ограничение по времени.
