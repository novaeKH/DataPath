# Агрегации SQL: из событий в показатели

Четыре заказа — это четыре события. Для отчёта по клиентам нужны другие строки: одна строка на клиента, число заказов, общая и средняя сумма. Агрегация меняет уровень результата, поэтому перед `GROUP BY` полезно закончить фразу: «в результате одна строка соответствует…».

Рассмотрим клиентов с известными и неизвестными суммами. Это сразу покажет, почему разные способы подсчёта могут дать разные ответы.

## Полностью воспроизводимый пример

Конструкция `WITH ... AS (VALUES ...)` ниже задаёт временные учебные строки внутри одного запроса. Подробно CTE разберём позже; сейчас её можно воспринимать как маленькую таблицу `orders`.

```sql
WITH orders(client_id, amount) AS (
    VALUES (1, 100.0), (1, 50.0), (2, 200.0), (2, NULL)
)
SELECT
    client_id,
    COUNT(*) AS order_count,
    COUNT(amount) AS known_amount_count,
    SUM(amount) AS total,
    AVG(amount) AS mean_amount
FROM orders
GROUP BY client_id
ORDER BY client_id;
```

Для клиента 1 получится `2, 2, 150, 75`. Для клиента 2 — `2, 1, 200, 200`. `COUNT(*)` считает строки, `COUNT(amount)` — известные суммы. `AVG` усредняет известные значения, поэтому у клиента 2 среднее не равно 100.

Именно поэтому нельзя назвать любой `AVG(amount)` средним чеком без проверки полноты сумм. Если неизвестные суммы систематически отличаются, показатель будет смещён.

## Как работает GROUP BY

База собирает строки с одинаковыми значениями ключей в группы. Затем каждая агрегатная функция сворачивает значения своей группы. Результат содержит одну строку на комбинацию ключей.

Если группировать по `client_id, month`, получится одна строка на клиента и месяц. Добавление ключа делает результат подробнее. Удаление ключа объединяет ранее раздельные группы.

В `SELECT` обычно должны быть ключи группировки и агрегаты. Выбор случайного неагрегированного столбца не даёт осмысленного значения «для всей группы». SQLite допускает некоторые такие запросы, но переносимый и понятный SQL не должен зависеть от произвольной строки.

## WHERE отбирает события, HAVING отбирает группы

Нужно найти клиентов, у которых сумма заказов не меньше 150. Фильтровать требуется результат агрегации:

```sql
WITH orders(client_id, amount, status) AS (
    VALUES (1, 100.0, 'paid'), (1, 50.0, 'paid'),
           (2, 200.0, 'cancelled'), (2, 80.0, 'paid')
)
SELECT client_id, SUM(amount) AS total
FROM orders
WHERE status = 'paid'
GROUP BY client_id
HAVING SUM(amount) >= 150
ORDER BY client_id;
```

Сначала `WHERE` исключит отменённый заказ. Затем суммы станут равны 150 и 80. После `HAVING` останется клиент 1.

Если сначала сгруппировать все статусы, сумма клиента 2 будет 280. Это другой вопрос, а не другой способ получить тот же результат. Формулировка показателя должна определять порядок отбора.

## Условные показатели в одном запросе

Иногда нужно сохранить всех клиентов и рядом посчитать только часть событий. Условное выражение `CASE` возвращает выбранное значение:

```sql
WITH orders(client_id, amount, status) AS (
    VALUES (1, 100.0, 'paid'), (1, 50.0, 'cancelled'), (2, 80.0, 'paid')
)
SELECT
    client_id,
    COUNT(*) AS all_orders,
    SUM(CASE WHEN status = 'paid' THEN 1 ELSE 0 END) AS paid_orders,
    SUM(CASE WHEN status = 'paid' THEN amount ELSE 0 END) AS paid_total
FROM orders
GROUP BY client_id
ORDER BY client_id;
```

Для клиента 1 получится два события, одно оплаченное, оплаченная сумма 100. `WHERE status='paid'` заранее удалил бы отменённый заказ, и количество всех событий стало бы неверным для поставленной задачи.

Для доли умножьте числитель на `1.0`, чтобы не получить целочисленное деление. Если знаменатель может быть нулём, нужно отдельное правило для такого случая.

## Уникальные объекты и повторная агрегация

`COUNT(DISTINCT client_id)` считает уникальные известные идентификаторы, а не строки. Но `DISTINCT` не исправляет неправильную единицу наблюдения автоматически.

Среднее средних не всегда равно общему среднему. Если у одного клиента два заказа со средним 100, а у другого восемь со средним 200, общее среднее равно `(2*100 + 8*200)/10 = 180`, а не 150. При повторной агрегации храните суммы и количества, чтобы учитывать веса групп.

## Самопроверка и практика

1. Почему `COUNT(*)` и `COUNT(amount)` различаются?
2. Где отбирать оплаченные события, а где клиентов с большой суммой?
3. Почему сумма после добавления лишнего ключа может разбиться на несколько строк?
4. Когда допустимо усреднить средние без весов?

Разбор: пропуски не входят во второй подсчёт; `WHERE` работает со строками, `HAVING` с группами; изменился уровень результата; одинаковые веса подходят только соответствующему вопросу, например среднему по равнозначным группам, а не автоматически по событиям.

**Практика.** В первом примере посчитайте долю известных сумм по клиенту. Ожидаются 1.0 и 0.5. Объясните, почему это показатель полноты данных, а не вероятность оплаты.

В визуализации сравните число строк до и после группировки. Следующий урок покажет, как соединение таблиц может незаметно изменить эти количества.
