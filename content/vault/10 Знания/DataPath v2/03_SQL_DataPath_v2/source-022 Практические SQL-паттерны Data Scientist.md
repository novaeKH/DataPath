# Аналитические SQL-паттерны: от определения к запросу

На собеседовании задача часто звучит коротко: «посчитайте удержание» или «найдите лучшие товары». За знакомым названием скрываются разные определения. Удержание на следующий календарный день отличается от возврата когда-нибудь позже; два лучших товара отличаются от всех товаров на двух лучших уровнях выручки.

Надёжный подход: определить сущность и время, выбрать уровень промежуточных таблиц, вычислить показатель, затем проверить на небольшом примере вручную.

## Последняя версия и лучшие объекты в группе

Для последней версии сущности используйте `ROW_NUMBER` с разбиением по ключу и обратным порядком времени. Для ровно двух лучших объектов группы тоже нужен `ROW_NUMBER`, но с порядком по показателю и правилом разрешения равенства.

Если равные показатели должны иметь одинаковое место, нужны `RANK` или `DENSE_RANK`. Само название «top-2» не определяет политику равенства. Уточните её до запроса и покажите пример с одинаковыми значениями.

Дедупликация — частный случай выбора записи. Нужно объяснить, почему сохраняется именно последняя версия, наиболее полная запись или запись из приоритетного источника. Удаление случайной строки не является определением качества.

## Удержание на следующий день

Определим D1 retention: доля пользователей, которые вернулись на следующий календарный день после первого появления. Один пользователь учитывается один раз, независимо от числа событий.

```sql
WITH
events(user_id, day) AS (
    VALUES (1, '2026-01-01'), (1, '2026-01-02'), (1, '2026-01-02'),
           (2, '2026-01-01'), (3, '2026-01-02'), (3, '2026-01-03')
),
first_seen AS (
    SELECT user_id, MIN(day) AS cohort_day
    FROM events
    GROUP BY user_id
),
flags AS (
    SELECT f.user_id, f.cohort_day,
        EXISTS (
            SELECT 1 FROM events e
            WHERE e.user_id = f.user_id
              AND e.day = date(f.cohort_day, '+1 day')
        ) AS returned_d1
    FROM first_seen f
)
SELECT cohort_day, COUNT(*) AS users,
       SUM(returned_d1) AS returned_users,
       1.0 * SUM(returned_d1) / COUNT(*) AS retention_d1
FROM flags
GROUP BY cohort_day
ORDER BY cohort_day;
```

У когорты 1 января два пользователя, вернулся один: удержание 0.5. У когорты 2 января один пользователь, он вернулся: 1.0. Повторное событие пользователя 1 не изменило числитель благодаря `EXISTS`.

Когорта — группа с общим моментом начала наблюдения. Для свежей когорты следующий день может ещё не наступить. Такие пользователи не должны автоматически считаться невозвратившимися: нужен завершённый горизонт наблюдения.

## Воронка требует порядка событий

Пусть этапы — просмотр, добавление в корзину, оплата. Подсчёт пользователей, у которых когда-либо были все три события, не гарантирует прохождение последовательной воронки. Оплата могла относиться к другой покупке или произойти раньше выбранного просмотра.

Определите связующую сущность: пользователь, сессия или заказ. Затем задайте допустимый промежуток и порядок времени. Например, оплата должна относиться к тому же заказу и наступить после добавления в корзину.

Каждый промежуточный результат должен иметь понятный ключ. Если соединить все просмотры со всеми оплатами пользователя, события размножатся. Обычно сначала выбирают подходящие времена этапов или используют условие существования.

## Сессии из разрывов между событиями

Сессию можно определить как последовательность событий, между которыми не больше 30 минут. Это условное аналитическое определение, а не универсальный закон поведения пользователя.

Механизм состоит из трёх шагов. Через `LAG` получаем время предыдущего события внутри пользователя. Отмечаем новую сессию у первого события и после разрыва больше порога. Накопленная сумма этих отметок даёт номер сессии.

В SQLite разность `julianday(current) - julianday(previous)`, умноженная на 1440, выражает минуты. Граница «больше 30» отличается от «не меньше 30». Для точной проверки используйте небольшой пример с событиями через 29, 30 и 31 минуту.

## Временные признаки для ML

Для каждого момента прогноза сначала отберите доступную историю, затем считайте число событий, сумму и давность последнего события. Будущая покупка может определять целевую переменную, но не должна попадать в исторические признаки.

Кроме даты события учитывайте задержку поступления данных. Вчерашний заказ, загруженный сегодня, не был известен вчерашней системе. Если историческое моделирование игнорирует это, оценка качества окажется завышенной.

Проверяйте результат на одном конкретном пользователе вручную. Несколько правильно прослеженных строк часто обнаруживают ошибку, которую не видно в итоговом среднем.

## Самопроверка и практика

1. Почему число событий не годится числителем пользовательского удержания?
2. Почему свежие когорты нельзя сравнивать со старыми без учёта горизонта?
3. Почему три встреченных типа событий ещё не образуют воронку?
4. Как получить номер сессии из признака её начала?

Разбор: один человек может создать несколько событий; наблюдение ещё не завершено; нужны порядок и общая сущность; накопленной суммой по пользователю.

**Практика.** Добавьте пользователю 2 событие 3 января. D1 для когорты 1 января останется 0.5: это возврат на второй день. Затем добавьте ему событие 2 января; D1 станет 1.0. Объясните различие без запуска запроса, затем проверьте.

В SQL-практикуме применяйте эти определения к Olist и сверяйте отношения таблиц со схемой. Успех — не просто выполняющийся запрос, а ответ на точно сформулированный вопрос.
