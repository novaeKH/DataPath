# JOIN: соединяем сущности без потери и размножения данных

У клиента есть город, у заказа — сумма. Чтобы посчитать выручку по городам, нужно связать таблицы. Ошибка соединения часто не вызывает исключение: запрос успешно возвращает строки, но одна сумма учитывается дважды.

Главная проверка перед `JOIN` — сколько совпадений допустимо для каждой строки. Начнём с отношения «один клиент — много заказов».

## Маленький пример соединения

```sql
WITH
clients(client_id, city) AS (
    VALUES (1, 'Казань'), (2, 'Москва'), (3, 'Пермь')
),
orders(order_id, client_id, amount) AS (
    VALUES (101, 1, 100), (102, 1, 50), (103, 2, 200)
)
SELECT c.client_id, c.city, o.order_id, o.amount
FROM clients AS c
LEFT JOIN orders AS o ON o.client_id = c.client_id
ORDER BY c.client_id, o.order_id;
```

Клиент 1 даст две строки, клиент 2 — одну, клиент 3 — строку с `NULL` в полях заказа. Всего получится четыре строки. `LEFT JOIN` сохраняет строки слева, но не обещает сохранить их количество: одна левая строка может иметь несколько совпадений справа.

Псевдонимы `c` и `o` помогают указать, из какой таблицы взят столбец. Условие `ON` определяет, какие пары считаются совпавшими.

## INNER и LEFT отвечают на разные вопросы

`INNER JOIN` оставляет только совпавшие пары. В нашем примере клиент 3 исчезнет. Это подходит для вопроса «какие клиенты делали заказы», но не для вопроса «сколько заказов у каждого клиента, включая ноль».

После левого соединения отсутствующий заказ обозначается `NULL`. Поэтому при группировке клиентов нужно считать `COUNT(o.order_id)`, а не `COUNT(*)`: сохранённая строка клиента без заказа иначе будет ошибочно посчитана как один заказ.

```sql
WITH
clients(client_id) AS (VALUES (1), (2), (3)),
orders(order_id, client_id) AS (VALUES (101, 1), (102, 1), (103, 2))
SELECT c.client_id, COUNT(o.order_id) AS order_count
FROM clients c
LEFT JOIN orders o ON o.client_id = c.client_id
GROUP BY c.client_id
ORDER BY c.client_id;
```

Ожидаемые количества: 2, 1, 0. Это самостоятельный пример, не требующий созданных заранее таблиц.

## Откуда берутся лишние строки

Если в справочнике клиента 1 случайно две строки, а заказов у него три, соединение даст шесть пар. Обе стороны содержат повторы ключа: возникает отношение «многие ко многим».

Ещё опаснее соединить сразу две дочерние таблицы: три заказа и четыре обращения клиента дадут двенадцать комбинаций. Сумма заказов повторится по числу обращений. Обычно сначала каждую дочернюю таблицу агрегируют до одной строки на клиента, затем соединяют агрегаты.

`DISTINCT` не является общим исправлением: разные настоящие заказы могут иметь одинаковые суммы, а лишние строки — различаться второстепенными полями. Нужно исправить отношение ключей.

## Условие в ON и условие в WHERE

Нужно сохранить всех клиентов и присоединить только оплаченные заказы. Условие статуса относится к поиску совпадений:

```sql
WITH
clients(client_id) AS (VALUES (1), (2), (3)),
orders(order_id, client_id, status) AS (
    VALUES (101, 1, 'paid'), (102, 2, 'cancelled')
)
SELECT c.client_id, o.order_id
FROM clients c
LEFT JOIN orders o
    ON o.client_id = c.client_id AND o.status = 'paid'
ORDER BY c.client_id;
```

Останутся три клиента: у первого заказ 101, у остальных `NULL`. Если перенести `o.status='paid'` в `WHERE`, строки без оплаченного совпадения будут отфильтрованы. Левое соединение фактически перестанет сохранять нужную группу.

## Отсутствие совпадений и соединение таблицы с собой

Чтобы найти клиентов без заказов, используют левое соединение и `WHERE o.order_id IS NULL`, если идентификатор реального заказа не может быть `NULL`. Другой ясный способ — `NOT EXISTS`, который проверяет отсутствие подходящей строки. Его разберём в следующем уроке.

Соединение таблицы с собой, или self join, использует два псевдонима одной таблицы. Например, сотрудник и его руководитель представлены разными строками справочника. Это не особый математический тип соединения: меняется только источник обеих сторон.

## Самопроверка и практика

1. Почему левое соединение может увеличить число строк?
2. Почему `COUNT(*)` даёт неверный ноль заказов?
3. Чем опасно одновременное соединение заказов и обращений?
4. Когда фильтр справа должен находиться в `ON`?

Разбор: совпадений может быть несколько; сохранённая строка клиента тоже считается; появляются все комбинации дочерних событий; когда требуется ограничить совпадения, сохранив все левые сущности.

**Практика.** Измените первый запрос так, чтобы остались только клиенты без заказов. Ожидается клиент 3. Затем добавьте клиенту 3 заказ и убедитесь, что результат пуст. Предскажите число строк до запуска.

В визуализации следите за конкретным ключом, а не только общей таблицей. В SQL-практикуме используйте схему Olist, чтобы установить связи заказов, товаров и платежей.
