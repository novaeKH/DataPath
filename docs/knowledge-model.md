# DataPath — персональная модель знаний

## Принципы

1. **Многомерность, а не один процент.** Оценка по разным осям (теория, код, объяснение…), агрегированных процентов нет по умолчанию.
2. **Прозрачность.** Пользователь видит, на чём основана каждая оценка.
3. **Объяснимость.** Система говорит не «знаешь на 72%», а «можешь объяснить, но путаешь допущения».
4. **Без ложной точности.** Оценки обновляются по байесовским правилам (conjugate priors) — они консервативны при малом количестве evidence.
5. **Отдельные evidence, а не суммарный балл.** Каждое измерение обновляется независимо.

## Оси оценки (Axes)

Каждый `skill_id` (из Learning Catalog) оценивается по 7 осям. Не каждый skill требует всех осей — некоторые специфичны для типа навыка.

| Ось | ID | Что измеряет | Как собирается evidence |
|---|---|---|---|
| **Теория** | `theory` | Понимание механизма, формул, допущений | Free-recall, вопросы на понимание, сцена `retrieval` |
| **Воспроизведение** | `reproduce` | Способность воспроизвести без подсказки | Free-recall с пустым полем, вопросы «объясни своими словами» |
| **Применение** | `apply` | Решение задачи в стандартных условиях | Микро-задачи, упражнения, сцена `application` |
| **Код** | `code` | Написание работающего кода | Код-сцены, мини-кейсы, проекты |
| **Интерпретация** | `interpret` | Анализ результатов, метрик, ошибок | Анализ output, выбор метрики, error analysis |
| **Объяснение** | `explain` | Связный устный/письменный ответ | AI-оценка объяснения, Interview-режим |
| **Собеседование** | `interview` | Ответ в стрессовом формате | Interview-режим кейса, вопросы с таймером |

**Не все оси нужны каждому навыку:** для `sql.aggregation` важны `code` и `apply`, но не `theory`. Для `ml.bias_variance_regularization` важны `theory` и `explain`.

## Модель данных

```sql
-- Оценка по одной оси для одного навыка
CREATE TABLE skill_assessment (
    skill_id       TEXT NOT NULL,     -- ml.tree_ensembles
    axis           TEXT NOT NULL,     -- theory
    alpha          REAL NOT NULL,     -- Байесовский prior: «успехи»
    beta           REAL NOT NULL,     -- Байесовский prior: «неуспехи»
    evidence_count INTEGER NOT NULL,  -- Количество измерений
    last_updated   TEXT NOT NULL,
    PRIMARY KEY (skill_id, axis)
);
```

**Почему alpha/beta, а не score:**
- `score = alpha / (alpha + beta)` — ожидаемое значение Beta-распределения
- При малом количестве evidence (alpha+beta мало) — оценка около prior (~0.5)
- При росте evidence — оценка сходится к реальной частоте успехов
- Это даёт естественный «режим новичка» без ручного threshold

**Начальные значения:** `alpha = 2, beta = 2` → score = 0.5, evidence_count = 0 (слабая уверенность)

## Как обновляются оценки

После каждого измерения (сцена урока, упражнение, кейс):

```python
def update_skill(skill_id, axis, success: float):
    """
    success: 0.0 (полная неудача) .. 1.0 (идеальный результат)
    Для бинарных: 0 или 1
    Для рубрик: среднее по элементам (weighted)
    """
    entry = get(skill_id, axis)
    
    # Байесовское обновление с учётом «веса» evidence
    weight = 1.0  # может варьироваться по типу сцены
    entry.alpha += success * weight
    entry.beta += (1 - success) * weight
    entry.evidence_count += 1
    entry.last_updated = now()
```

**Weight evidence по типу:**
- Free-recall без подсказки → weight = 1.2 (сильный сигнал)
- Multiple choice без подсказки → weight = 0.5 (слабый сигнал)
- Multiple choice с подсказкой → weight = 0.2 (очень слабый)
- Мини-кейс → weight = 1.5 (интегративный сигнал)
- Итоговый кейс → weight = 2.0 (самый сильный сигнал)

### Рубрики для диагностик (из Learning Catalog)

В Learning Catalog каждый `skill.diagnostics[].rubric[]` содержит элементы с весом. При оценке AI-наставник или интерактивный компонент ставит баллы (0/0.5/1) по каждому элементу. Итоговый `success` = взвешенное среднее.

Пример: диагностика `diag.tree-ensembles.1` (сравнение дерева, RF и boosting):
```json
[
  {"id": "tree", "weight": 0.25, "score": 1},    // ✓ описал greedy
  {"id": "forest", "weight": 0.35, "score": 0.5}, // ~ упомянул усреднение, но без decorrelation
  {"id": "boosting", "weight": 0.4, "score": 0}   // ✗ перепутал с бэггингом
]
// success = 1*0.25 + 0.5*0.35 + 0*0.4 = 0.425
```

## Типичные ошибки

В Learning Catalog для каждого навыка задан `error_taxonomy`:

| Код ошибки | Описание |
|---|---|
| `missing_definition` | Не может дать определение |
| `confuses_concepts` | Путает связанные концепции |
| `wrong_assumption` | Ошибочное предположение |
| `data_leakage` | Пропустил утечку данных |
| `wrong_validation` | Неправильный split/оценка |
| `metric_mismatch` | Неподходящая метрика |
| `cannot_explain` | Не может объяснить |
| `needs_hint` | Нужна подсказка |
| `careless_error` | Случайная ошибка |

Каждая диагностика привязана к кодам ошибок (`error_codes`). При оценивании система фиксирует, какие коды сработали.

```sql
CREATE TABLE error_log (
    id           INTEGER PRIMARY KEY,
    skill_id     TEXT NOT NULL,
    diagnostic_id TEXT NOT NULL,    -- какая диагностика
    error_code   TEXT NOT NULL,     -- какой тип ошибки
    axis         TEXT NOT NULL,     -- на какой оси проявилась
    context      TEXT,              -- урок/кейс/сцена
    created_at   TEXT NOT NULL
);
```

## Определение слабых тем

«Слабая» тема определяется не по одному проценту, а по комбинации:

1. **Низкая консервативная оценка:** `alpha / (alpha + beta) < 0.6` при `evidence_count >= 2`
2. **Стагнация:** оценка не растёт 3+ попыток подряд
3. **Повторяющиеся ошибки одного типа:** `confuses_concepts` встречается ≥ 2 раз для одного skill_id
4. **Критические пробелы:** навык является prerequisite для текущего материала, но оценка < 0.5

## Избегание ложной точности

- **Минимум 2 evidence до показа оценки пользователю.** До этого показывается «недостаточно данных».
- **Байесовское среднее** даёт консервативную оценку при малом N.
- **Не показывать проценты в UI для осей с evidence_count < 3.** Вместо этого — качественные уровни.
- **Уровни вместо процентов:**

| Score range | Отображение |
|---|---|
| 0.0–0.3 | «Начало» |
| 0.3–0.5 | «Основы» |
| 0.5–0.7 | «Понимание» |
| 0.7–0.85 | «Уверенно» |
| 0.85–1.0 | «Свободно» |

## Правила MVP (без сложного ML)

В MVP достаточно:

1. **Байесовское среднее** — простая и объяснимая модель.
2. **Обновление по рубрикам** — без NLP/автооценки смысла (AI-наставник может оценивать, но алгоритм остаётся простым).
3. **Фиксация кодов ошибок** — без кластеризации/ML.
4. **Простые правила для слабых тем** — пороговые значения.
5. **Приоритет повторения** — взвешенная сумма, а не ML-модель forgetting curve.

## Отображение в Atlas

Узел темы в Atlas показывает комбинированное состояние:

```
Внешнее кольцо: общее состояние
├── Серое    — не изучалось
├── Контур   — доступно (пройдены prerequisites)
├── Частично — изучается (≥ 1 evidence)
├── Заполнено — уверенное владение (среднее по осям ≥ 0.75)
└── Пульсирует — требует повторения

Внутреннее заполнение: прогресс theory + apply + code
├── Пусто   — 0–25%
├── Четверть — 25–50%
├── Половина — 50–75%
└── Полное  — 75–100%

Цвет кольца:
├── Зелёный (акцент области) — норма
├── Оранжевый — начинает забываться (давность > 7 дней)
└── Красный — обнаружен пробел
```
