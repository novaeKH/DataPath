# DataPath — архитектурные решения

## 1. Технологический стек MVP

### Frontend

| Компонент | Выбор | Почему | Отклонённые альтернативы |
|---|---|---|---|
| Фреймворк | React 18+ | Зрелая экосистема, хуки, сообщество | Svelte (хорош, но меньше библиотек для визуализаций) |
| Язык | TypeScript | Безопасность типов, лучшая поддержка IDE | JavaScript (без типов сложнее поддерживать) |
| Сборка | Vite | Мгновенный HMR, простой конфиг, быстрый билд | Next.js (избыточен без SSR/SEO для локального приложения) |
| Роутинг | React Router v7 | Стандарт для SPA, ленивая загрузка | TanStack Router (моложе, меньше adoption) |
| Стилизация | Tailwind CSS v4 + CSS переменные | Быстрая разработка, две темы через переменные, tree-shaking | CSS Modules (больше boilerplate), styled-components (runtime overhead) |
| Анимации | Framer Motion | Декларативные анимации, отличная поддержка React, `layoutId` для переходов Atlas→Focus | GSAP (императивный, мощнее но сложнее), react-spring (хорош, но меньше adoption) |
| Графики | Recharts | Декларативные React-компоненты, хорош для confusion matrix, PR/ROC, метрик | D3.js (низкоуровневый, больше кода для стандартных графиков) |
| Атлас знаний | D3.js + React (кастомный canvas/SVG) | Полный контроль над интерактивной визуализацией графа с zoom/pan | Cytoscape.js (тяжеловат для нашей задачи), vis.js (менее гибкий) |
| Состояние | Zustand | Минимальный boilerplate, простая модель, хорош для средних приложений | Redux Toolkit (избыточен для MVP), Jotai (атомарный — хорошо, но Zustand проще) |
| HTTP-клиент | Встроенный fetch + SSE | Всё что нужно для REST + стриминг, без зависимостей | Axios (лишняя зависимость), TanStack Query (полезно позже, не для MVP) |

### Backend

| Компонент | Выбор | Почему | Отклонённые альтернативы |
|---|---|---|---|
| Фреймворк | FastAPI | Быстрый, асинхронный, авто-документация (OpenAPI), нативная поддержка SSE | Django (избыточен без админки/ORM), Flask (нет асинхронности из коробки) |

### RAG и AI

| Компонент | Выбор | Почему | Отклонённые альтернативы |
|---|---|---|---|
| Embedding-хранилище | ChromaDB | Встроенный SQLite, простой API, Python-нативный, локальный | FAISS (мощнее, но сложнее API, нет metadata), Qdrant (избыточен локально) |
| Embedding-модель | **`bge-m3`** через Ollama | Мультиязычная (хороший русский), 1024-мерный вектор, ~1.5 ГБ RAM | `nomic-embed-text` (меньше, но слабее для русского), `all-MiniLM-L6-v2` (английский) |
| LLM | **`qwen2.5:3b-instruct`** через Ollama | Отличный русский язык, ~2.5 ГБ RAM, приемлемая скорость (~25 ток/с на M4) | `llama3.2:3b` (слабее русский), `gemma3:4b` (средний русский), `phi3:mini` (слабый русский) |
| Reranker | **Пропущен в MVP** | Не включаем до этапа 2: добавил бы ~1 ГБ RAM и ~1 с задержки. Вернуться после оценки качества retrieval на тестовых вопросах | `bge-reranker-v2-m3` |
| Фреймворк RAG | Собственный pipeline (без LangChain) | Полный контроль, меньше абстракций, проще отладка | LangChain (слишком много абстракций), LlamaIndex (избыточен) |
| Markdown-парсер | `markdown-it-py` + `python-frontmatter` | Извлекает frontmatter, AST для чанкинга | `mistune` (быстрее, но меньше фич) |

## 2. Почему не [популярная альтернатива]

### Vite, а не Next.js
- Приложение — SPA для локального запуска. Нет SEO, нет SSR.
- Next.js добавляет сложность (серверные компоненты, middleware, маршрутизацию на файловой системе) без выгоды для локального SPA.
- Vite проще для разработки: мгновенный HMR, меньше абстракций.

### SQLite, а не PostgreSQL
- Один пользователь, локально. Нет конкурентных записей.
- Ноль настройки: файл создаётся автоматически.
- WAL-режим даёт достаточную конкурентность чтения/записи.
- При необходимости миграция на PostgreSQL потребует только смену connection string (SQLAlchemy абстрагирует диалект).

### Собственный RAG pipeline, а не LangChain
- LangChain добавляет ~30 зависимостей, большую поверхность для багов.
- Для одного формата документов (структурированный Markdown с заголовками) кастомный пайплайн в ~300 строк понятнее и надёжнее.
- Полный контроль над чанкингом, дедупликацией и цитированием.

### ChromaDB, а не FAISS
- FAISS требует ручного управления index → disk, metadata хранится отдельно.
- ChromaDB даёт из коробки: хранение embeddings + metadata, фильтрацию, обновление.
- Для MVP с <10 000 чанков производительность ChromaDB избыточно достаточна.

### Zustand, а не Redux
- Меньше кода в 3–5 раз для того же функционала.
- Не требует middleware для асинхронных действий.
- Простая модель: `create → (set, get) → store`. Достаточно для MVP.

## 3. Ключевые компромиссы

1. **Простота > масштабируемость.** Всё спроектировано для одного пользователя локально. При необходимости масштабирования потребуется реархитектура (очереди, PostgreSQL, распределённый RAG) — это осознанный выбор.

2. **Markdown как единственный source of truth.** Контент живёт в `content/vault`, приложение только читает и кэширует. Это даёт: офлайн-редактирование в Obsidian, версионирование через Git, отсутствие CMS.

3. **AI-модели через Ollama, а не облачные API.** Это даёт: полную локальность, приватность, отсутствие платы за токены. Но ограничивает размер модели (~3B параметров при 16 ГБ RAM). Качество ответов ниже, чем у GPT-4/Claude. Для MVP это приемлемо.

4. **Отсутствие аутентификации.** Один пользователь, локально. Не нужны: логин, пароль, сессии, OAuth. Экономит ~30% кода бэкенда.

5. **Интерактивные компоненты — кастомные React, а не Jupyter.** Jupyter-подход (встроенный Python в браузере через Pyodide) сложен для production-UI и потребляет много памяти. Проще сделать интерактивные визуализации на JS/D3 с предпросчитанными на бэкенде сценариями.

## 5. Архитектурная граница (явное разделение)

**Backend (Python/FastAPI) — вся содержательная логика:**
- Парсинг и каталогизация контента (`content/vault`)
- Модель знаний (байесовские оценки, обновление alpha/beta)
- Очередь повторения (SM-2, приоритизация)
- Проверка упражнений и кейсов (рубрики, коды ошибок)
- RAG-pipeline (чанкинг, embedding, retrieval, сборка промпта)
- Взаимодействие с Ollama (генерация, стриминг)
- Валидация целостности vault
- Все вычисления и бизнес-правила

**Frontend (React/TypeScript) — только интерфейс:**
- Визуализация (Atlas, графики, интерактивные лабы)
- Анимации и переходы (Framer Motion)
- Пользовательский ввод и навигация
- Отображение данных, полученных от API
- Локальное состояние UI (тема, открытые панели, zoom)
- Стриминг-клиент для AI-ответов (SSE)

- Принимать решения о следующем шаге/повторении на клиенте
- Реализовывать чанкинг/retrieval на клиенте
